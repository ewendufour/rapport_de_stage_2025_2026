\subsection*{Contexte général} 
Les assistants de preuves sont des logiciels permettant de formaliser des résultats mathématiques et 
ainsi d'aider leurs utilisateurs à rédiger des preuves correctes. 
Certains assistants à la preuve, tels que Rocq \cite{rocq}, Lean \cite{demoura2021lean4} ou Agda \cite{norell2008agda}, 
s'appuient sur la théorie des types dépendants pour représenter les énoncés mathématiques et leurs preuves.
Au sein de ces systèmes, un énoncé est représenté par un type, tandis qu'une preuve est représentée par un terme habitant ce type.
Le problème de l'habitation des types constitue donc un enjeu majeur dans le domaine de la formalisation automatisée.

Canonical \cite{norman2025canonical} est un logiciel de recherche de preuve 
se basant sur une théorie des types dépendants dont le format est optimisé pour la recherche de termes.
Son intégration dans l’assistant de preuve Lean a montré que cette approche 
s’intègre particulièrement bien aux assistants de preuves fondés sur la théorie des types dépendants. 
Elle présente notamment des performances supérieures à celles des autres logiciels de recherche de preuves disponibles dans Lean.

\subsection{La théorie des types dépendants.}

\paragraph{Un système de preuves.}
Une théorie des types est un système formel dans lequel on s’intéresse notamment aux programmes bien typés. 
Celle-ci est définie par un ensemble de termes (programmes) constructibles, un ensemble de types constructibles, 
ainsi qu’un ensemble de règles de typage permettant d’attribuer des types aux termes et de définir les conversions entre types.
Nous notons $\mathsf{t : T}$ pour indiquer qu'un terme $\mathsf{t}$ est de type $\mathsf{T}$ et $\mathsf{\Gamma \vdash t : T}$ 
que le contexte $\mathsf{\Gamma}$ permet de déduire que $\mathsf{t}$ est de type $\mathsf{T}$.

\paragraph{Correspondance de Curry-Howard.}
Dans ses travaux \cite{howard1980formulae}, Howard établit un lien profond entre les propositions de la logique intuitionniste et les types.
Via cette correspondance, prouver qu'une formule $\mathsf{A}$ est vraie revient à exhiber un programme construisant un objet de type $\mathsf{A}$.
En enrichissant nos types en permettant aux types de dépendre de termes, 
on obtient un système de preuves dans lequel on peut décrire tous les énoncés mathématiques, la théorie des types dépendants \cite{martinlof1984intuitionistic}.

\paragraph{Assistants à la preuve.}
Les assistants à la preuve comme Rocq, Lean et Agda sont basés sur des théories des types dépendants.
Dans ces systèmes, on décrit un énoncé à prouver via un type, et une preuve de cet énoncé via un terme qui à le type correspondant. 
L'assistant vérifie que le terme possède le bon type avec un algorithme de type-checking \cite{coquand1996algorithm}. 
Dans la figure \ref{fig:agda-proof}, la première ligne permet de spécifier le type (l'énoncé) à prouver, 
et la deuxième décrit un terme (une preuve) de ce type dans la syntaxe d'Agda\footnote{Le manuel de référence d'Agda : \url{https://agda.readthedocs.io/en/latest/}}.

\subsection{La théorie cubique des types}
\subsubsection{La théorie homotopique des types.}
En mathématiques, on étudie souvent des objets à travers différentes représentations. 
Cependant, les propriétés intrinsèques de ces objets ne dépendent pas de la représentation choisie. 
Par exemple, un graphe peut être étudié à travers sa liste d’adjacence ou sa matrice d’adjacence.

C’est dans le but de formaliser cette indépendance vis-à-vis de la représentation que l’axiome d’univalence a été introduit par Voevodsky. 
Celui-ci stipule que, pour deux types, l’existence d’une équivalence entre ceux-ci est liée à l’existence d’une égalité entre ces deux types. 
Une équivalence entre deux types $\mathsf{A}$ et $\mathsf{B}$ est une fonction $\mathsf{f : A \to B}$ 
qui admet un inverse à gauche (une fonction $\mathsf{g : B \to A}$ avec $\mathsf{g \circ f = id}$) 
et un inverse à droite (une fonction $\mathsf{h : B \to A}$ avec $\mathsf{f \circ h = id}$)

Cet axiome constitue le principal ajout de la théorie homotopique des types \cite{hottbook} (HoTT). 
Celle-ci possède de nombreuses propriétés. 
Du point de vue du mathématicien, cette théorie se présente comme une alternative à la théorie des ensembles, 
tout en offrant des outils puissants pour développer l’homotopie synthétique. 
L’extensionnalité des fonctions et des propositions est également démontrable dans cette théorie.

Cependant, l’ajout de l’axiome d’univalence brisent les propriétés calculatoires de la théorie des types, 
car aucune règle de calcul ne lui est associée.

\subsubsection{Une interprétation constructive de l'univalence.}
Dans le but de retrouver ces propriétés calculatoires, la théorie cubique des types \cite{cohen2016cubical} a été introduite par Cohen, Coquand, Huber et Mörtberg.
Celle-ci ajoute un nouveau type $\mathsf{I}$ représentant l’intervalle $\mathsf{[0;1]}$ et donne une nouvelle interprétation de l’égalité.
Une preuve d’égalité entre deux termes $\mathsf{x}$ et $\mathsf{y}$ d’un type $\mathsf{A}$ est interprétée comme une fonction de l’intervalle vers le type $\mathsf{A}$ qui,
lorsqu’elle est évaluée en $\mathsf{0}$ (respectivement $\mathsf{1}$), doit être définitionnellement égale à $\mathsf{x}$ (respectivement $\mathsf{y}$).

Picturalement, une égalité en théorie cubique des types peut être représentée comme une arête,
une égalité entre égalités (une fonction de $\mathsf{I \times I \to A}$) comme un carré,
et une fonction de $\mathsf{I \times I \times I \to A}$ comme un cube, et ainsi de suite.

\subsubsection{La composition homogène}
Un autre ingrédient clé de la théorie cubique des types est l’opérateur de composition homogène.
Introduit dans le CCHM \cite{cohen2016cubical}, cet opérateur permet de compléter des cubes ouverts en dimension $\mathsf{n}$.
Pour cela, il suffit de lui spécifier un ensemble de faces cohérentes entre elles, ainsi qu’une base permettant de construire la face manquante.

Par exemple, dans la figure \ref{fig:hcomp}, les faces de gauche, de droite et du bas ont été fournies à l’opérateur $\mathsf{hcomp}$,
qui construit alors la face du haut.
Comme mentionné précédemment, pour que cet opérateur fonctionne, les faces fournies doivent être cohérentes aux endroits où elles se rencontrent.
Supposons que $\mathsf{i = i0}$ et $\mathsf{j = i0}$, correspondant au coin en bas à gauche.
Les deux arêtes qui se rencontrent doivent alors désigner un même terme, ici $\mathsf{a}$.

En dimension 3, cette contrainte de cohérence s’applique non plus à des coins, mais à des arêtes entières.
En dimension 4, elle s’applique à des faces, et ainsi de suite.

La seule implémentation disponible sur un assistant de preuve répandu de la théorie cubique des types est celle fournie par Cubical Agda \cite{vezzosi2019cubical}.
C'est pour cette raison que nous nous intéresserons à celui-ci dans le reste de ce travail.


\subsection{La preuve automatisée en théorie cubique des types.}
Un enjeu majeur de la théorie cubique des types est de parvenir à automatiser la recherche de preuves. 
Dans les théories des types dépendants plus classiques, il existe plusieurs classes d’outils permettant d’automatiser cette recherche.

Une première classe d’outils regroupe ceux qui cherchent à appliquer automatiquement des tactiques. 
On peut notamment citer Aesop \cite{limpberg2023aesop} dans Lean, ainsi que les nombreuses tactiques de Rocq permettant d’effectuer ce type de recherche, 
telles que \texttt{tauto} ou \texttt{firstorder}.

Une deuxième classe de prouveurs automatiques traduit les obligations de preuve dans une logique du premier ordre. 
C’est notamment le cas de Coqhammer \cite{czajka2018hammer} dans Rocq et de Sledgehammer \cite{bohme2010sledgehammer} dans Isabelle, 
qui transmettent ensuite les formules obtenues à des solveurs SMT ou des prouveurs automatiques tels que Vampire \cite{bartek2025vampire}, 
CVC5 \cite{barbosa2022cvc5} ou Z3 \cite{de2008z3}.

Enfin, une dernière classe regroupe les logiciels reposant directement sur l'habitation de types. 
C’est notamment le cas d’Agsy et de son successeur Mimer \cite{skystedt2022new} dans Agda.

À notre connaissance, aucune de ces approches n’est actuellement utilisée pour l’automatisation de la recherche de preuves en théorie cubique des types.

\section{Traduction d'Agda vers Canonical}
Dans cette section, nous présentons l’intégration de Canonical au sein d’Agda. 
Nous introduisons dans un premier temps Canonical, puis la solution étudiée pour permettre son utilisation depuis Agda. 
Nous terminons par la présentation de la méthode utilisée pour convertir les types d’Agda en types de Canonical.

\subsection{Canonical}
Canonical est un solveur pour les théories des types dépendants écrit en Rust par Norman et Avigad \cite{norman2025canonical}.
Celui-ci fonctionne sur sa propre théorie des types ce qui lui permet, entre autre, 
d'être totalement indépendant des assistants de preuves et de pouvoir potentiellement être utilisé avec plusieurs assistants.
Il suffit de l'ajouter comme un plugin et de transformer les énoncés de l'assistant à la preuve en types de Canonical,
les lui fournir pour qu'il effectue sa recherche de preuves et, en cas de succès, traduire le résultat dans le langage de l'assistant à la preuve.
Dans leurs travaux \cite{norman2025canonical}, Norman et Avigad présentent une telle implémentation de Canonical dans l'assistant à la preuve Lean. 

\paragraph{Fonctionnement.} 
Étant donné un type, Canonical cherche à trouver un terme qui habite ce type en effectuant une recherche exhaustive en profondeur parmi les termes en forme normale. 
Le problème de l’habitation des types dans les théories des types dépendants étant semi-décidable, 
Canonical est ainsi garanti de trouver une solution au problème qui lui est soumis lorsqu’une telle solution existe.

Son implémentation dans Lean a montré des performances supérieures à celles d’Aesop et de Duper \cite{clune2024duper}, 
deux autres outils de recherche de preuves. 
Nous avons donc choisi d’utiliser Canonical pour notre prototype, dans l’objectif de l’appliquer à la théorie cubique des types.

\paragraph{Théorie des types.}
Afin de restreindre au maximum son espace de recherche tout en conservant un niveau d’expressivité élevé, 
Canonical repose sur sa propre théorie des types, présentée dans la figure \ref{fig:canonical-tt}.

Celle-ci possède un unique constructeur de termes, composé d’une liste de paramètres, 
d’une liste de déclarations \texttt{let}, d’un symbole de tête et d’une liste d’arguments. 
Un type de Canonical est un terme possédant des annotations de type sur ses lieurs (\texttt{let} et $\lambda$).

Chaque terme de Canonical doit être sous forme $\beta$-normale, c’est-à-dire qu’aucune $\beta$-réduction ne doit être possible au sein du terme. 
De plus, tout symbole d’arité $n$ doit être appliqué à exactement $n$ arguments, quitte à $\eta$-étendre les fonctions. 
Le symbole de tête du terme doit être lié par un `let` ou une $\lambda$-abstraction.

Au sein des types, chaque annotation de type est entièrement optionnelle. 
L’absence d’annotation de type pour un symbole indique à Canonical que celui-ci ne doit pas être utilisé pour construire le terme correspondant au but.

\paragraph{Définitions, constantes.} 
Canonical est capable de travailler avec des symboles représentant des constantes ainsi qu’avec des fonctions possédant une définition. 
Pour ce faire, il faut lui fournir, au moyen d’une déclaration \texttt{let}, le symbole ainsi que son type. 
Il est également possible de fournir à Canonical une définition associée à ce symbole, 
qui sont des règles de réécriture de la forme $\mathsf{f~a_1~a_2~a_n = g~b_1~b_2~b_m}$

Par exemple, supposons que l’on souhaite travailler avec la fonction $\mathsf{\_+\_}$ définie dans la figure \ref{fig:agda-nat}.

ainsi que les symboles $\mathsf{Z : \mathbb{N}}$ et $\mathsf{S : \mathbb{N} \to \mathbb{N}}$, 
il est également nécessaire de fournir à Canonical la définition du type $\mathsf{\mathbb{N}}$ ainsi que celles de ses symboles.

&(\_+\_ : \Pi (\_ : \mathbb{N}), (\_ : \mathbb{N}).\mathbb{N}) [zero + b = b ; suc~a + b = suc (a + b)],\\

\paragraph{Appel à Canonical.}
Dans le but d’aider l’utilisateur à compléter le but dans lequel il se trouve, 
nous souhaitons implémenter une commande permettant de récupérer le type du but courant et de le fournir à Canonical.

Deux solutions ont été envisagées afin de répondre à cette problématique. La première consiste à passer par le langage de réflexion d’Agda. 
Celui-ci permet d’écrire des tactiques de résolution directement sous la forme de termes d’Agda.

La deuxième solution consiste à implémenter une fonction permettant d’appeler Canonical directement dans le code Haskell d’Agda. 
Nous récupérons alors les types des buts dans la syntaxe interne des termes d’Agda puis, après une passe de transformation,

Comme nous souhaitons que notre prototype soit facilement utilisable, nous avons choisi de nous inspirer de la méthode employée,

\subsection{Cibles de la traduction}
La théorie des types de Agda étant différente de celle de Lean, 
nous devons adapter les techniques présentées dans les travaux de Norman et Avigad \cite{norman2025canonical} pour faire notre traduction.

\subsubsection{La syntaxe interne d'Agda}
Agda possède plusieurs syntaxes différentes pour représenter ses termes. 
Dans notre cas, nous nous intéressons à un sous-ensemble de la syntaxe dite interne des termes, 
dont une version simplifiée est présentée dans la figure \ref{fig:internal}.

Le sous-ensemble en question est décrit par quatre types mutuellement récursifs représentant respectivement les termes, 
les sortes, les types d’univers et les éliminateurs.

\begin{figure}[h]
\centering
\begin{minted}{haskell}

  | Lam ArgInfo (Abs Term)
  | Pi (Dom Term) (Abs Term)  
  | Def QName [Elim]              
  | Con ConHead ConInfo [Elim]
  | Sort Sort
  | Level Level

data Elim
  = Apply (Arg Term)

data Sort
  = Univ Univ (Level Term)

data Univ
  = UType

\end{minted}
\caption{Sous ensemble simplifié de la syntaxe interne des termes d'Agda.}
\label{fig:internal}
\end{figure}

\paragraph{Les termes.}
Les termes sont composés de variables, représentées par des indices de De Bruijn \cite{de1972lambda}, 
potentiellement appliquées à différents arguments, de $\lambda$-abstractions, ainsi que du type des fonctions dépendantes. 
Ils comprennent également des définitions, telles que les noms de fonctions ou de types inductifs, ainsi que des constructeurs, 
qui peuvent, eux aussi, être appliqués à différents arguments. Enfin, les termes peuvent contenir des sortes et des niveaux d’univers.

Dans la syntaxe réelle, les termes contiennent également d’autres constructions, 
telles que les littéraux ou les méta-variables, que nous n’aborderons pas dans ce travail.

\paragraph{Les éliminateurs.}
Au sein d'Agda, le type des éliminateurs permettent de représenter les applications de fonctions, 
les projections (types enregistrements) et les applications de chemin cubiques.
Pour le moment, nous ne nous interessons qu'aux applications.


\paragraph{Les sortes et types d'univers.}
Pour ce stage, nous avons choisi de restreindre notre prototype aux seules sortes liées aux petits univers et à leurs niveaux.

Nous expliquons ce choix par le fait que la majorité des cas testés ne présentaient pas d’autres sortes que celles-ci. 
De plus, au vu de la gestion des univers par Canonical, que nous détaillerons par la suite, 
ajouter la prise en charge d’autres constructions ne ferait qu’ajouter du bruit à la recherche de termes.



\subsubsection{La cible.}
Canonical est fourni avec une couche de compatibilité permettant de faire le lien avec le coeur du prover tout en gardant une syntaxe plus agréable à utiliser.
La figure \ref{fig:can-comp} montre la syntaxe pour représenter les termes et les types au sein de la couche de compatibilité en syntaxe Haskell.

\begin{figure}[h]
\centering
\begin{minted}{haskell}

\label{fig:can-comp}
\end{figure}

\paragraph{CDecl.}
Ce type décrit les déclarations de la forme $\mathsf{(x : A)}$.
Il est composé d'un symbole, éventuellement d'un type, et d'équations.

Si le champ \texttt{typ} n'est pas renseigné, cela peut avoir deux significations.

Dans le cas d'une déclaration \texttt{let}, cela indique à Canonical que le symbole ne doit pas être utilisé pour construire le résultat.
Dans le cas d'un paramètre, cela signifie que l'expression à laquelle la déclaration appartient représente un terme et non un type.

L'interprétation des équations associées aux déclarations dépend également du champ auquel ces dernières sont associées.
Dans le cas d'une déclaration \texttt{let}, les équations représentent les règles de réduction associées au symbole (e.g. définition d'une fonction).
Dans le cas d'un paramètre, elles représentent des contraintes de réduction sur ce paramètre.

\paragraph{CEquation.}
Ce type représente une règle de la forme $\mathsf{lhs = rhs}$ à travers deux spines (un symbole de tête et une liste arguments).
Par exemple, la déclaration associée à la fonction $\mathsf{not : Bool \to Bool}$, définie par $\mathsf{not~True = False}$ et $\mathsf{not~False = True}$,
possèdera deux équations dont les membres de gauche seront $\mathsf{CSpine~``not''~[trueExpr]}$ (resp. $\mathsf{CSpine~``not''~[falseExpr]}$) 
et les membres de droites seront $\mathsf{CSpine~``False''~[]}$ (resp. $\mathsf{CSpine~``True''~[]}$). 


\paragraph{CExpr.}
Ce type représente à la fois les termes et les types de Canonical que nous avons introduits dans la sous-section 2.1.
La distinction entre les termes et les types s'effectue au niveau des champs \texttt{params} et \texttt{lets}.
Contrairement aux types, un terme ne possédera pas d'annotations de type dans ces champs.

\paragraph{CSpine.}
Les spines sont composées d'un symbole de tête et d'une liste d'arguments.
Elles représentent le corps des types et des termes de Canonical.

\subsection{La traduction.}
Maintenant que nous avons présenté les langages source et cible, intéressons-nous à la traduction elle-même.
Notre traduction se décompose en trois fonctions mutuellement récursives permettant respectivement de transformer des termes en déclarations 
\texttt{toCDecl}, en expressions \texttt{toCExpr} ou en spines \texttt{toCSpine}.

\paragraph{Le point d'entrée.}
Canonical attend une déclaration en entrée pour effectuer son traitement. Notre point d'entrée est donc la fonction \texttt{toCDecl}, dont l'implémentation en Haskell est présentée en figure \ref{fig:agda-toCDecl}.
Celle-ci prend simplement en arguments un nom, un terme à convertir et un ensemble d'équations. Elle appelle ensuite la fonction \texttt{toCExpr} sur le terme à convertir afin de construire la structure \texttt{CDecl} correspondante.
Les autres arguments de la fonction sont utilisés dans des processus que nous détaillerons par la suite.



\begin{figure}[h]
\centering
\begin{minted}{haskell}
toCDecl :: Term -> -- ^ Le terme à convertir
           String -> -- ^ Le nom associé à la déclaration
           [CEquation] -> -- ^ Les contraintes / définitions
           [String] -> -- ^ Nom liés
           [CDecl] -> -- ^ Contexte
           Map String Bool -> -- ^ Définitions déjà rencontrées
           Bool -> -- ^ En train de transformer la déclaration "Goal"?
           TCM (CDecl, [CDecl], Map String Bool)
toCDecl t name eqs bindnames lets ald tplvl = do
  toCExpr t bindnames [] lets ald tplvl True
\end{minted}
\caption{Traduction des termes en CDecl.}
\label{fig:agda-toCDecl}
\end{figure}

\subsubsection{Conversion en termes de Canonical}
La fonction \texttt{toCExpr} a pour objectif principal de construire la liste des paramètres présents dans un terme ou un type de Canonical.
Pour ce faire, la fonction parcourt le terme en conservant les paramètres déjà créés jusqu'à ce qu'elle rencontre un terme qui n'en crée pas de nouveau.

\paragraph{Termes créant des paramètres.}
Deux constructeurs se traduisent en termes de Canonical : \texttt{Lam} et \texttt{Pi}.
Dans le cas de \texttt{Lam}, il suffit d'ajouter à la liste des paramètres une déclaration contenant uniquement le nom de la variable, puis de s'appeler récursivement sur le terme sous-jacent.
Dans le cas de \texttt{Pi}, deux situations doivent être distinguées.
Si nous sommes en train de convertir le terme en un type, il suffit de convertir le domaine du \texttt{Pi} en une \texttt{CDecl}, de l'ajouter aux paramètres, puis d'appeler récursivement \texttt{toCExpr} sur le codomaine.
Si nous sommes en train de convertir le terme en un terme, il faut le traduire selon le procédé décrit dans la section 4.1 de \cite{norman2025canonical}. Cette fonctionnalité n'a pas encore été implémentée dans notre prototype.
La distinction entre la traduction vers un terme ou vers un type s'effectue en fonction de la fonction appelant \texttt{toCExpr}.
Si celle-ci est appelée par \texttt{toCDecl}, cela signifie que nous sommes en train de convertir un type.
Dans le cas contraire, \texttt{toCExpr} a été appelée par \texttt{toCSpine} et nous sommes en train de convertir les arguments d'une fonction, qui sont donc des termes.

\paragraph{Autres constructeurs.}
Dans le cas ou \texttt{toCExpr} est appelé sur d'autre constructeur que \texttt{Pi} et \texttt{Lam}, cela signifie que tous les paramètres ont été dépliés.
Il faut donc convertir le termes vers une spine (constructeur de tête et arguments) et créer la \texttt{CExpr} en mettant les paramètres avec la spine.

Un point que nous n'avons pas encore abordé concerne la gestion du contexte du but.
Celui-ci sert à mettre tout ce qui est en lien avec les constantes, les fonctions externes, les datatypes et les constructeurs.
Notre stratégie consiste à mettre tout cet environnement sur l'expression correspondant au type du goal. 
L'environnement se construisant tout au long de la conversion du terme, nous devons le garder en mémoire et l'ajouter qu'à la toute fin de la traduction,
après avoir converti la spine du goal.
Nous détaillerons la construction de l'environnement par la suite.

\subsubsection{Conversion en spine.}
La fonction \texttt{toCSpine} sert à convertir les termes de Agda vers un symboles de tête et ses potentiels arguments.
Étant seulement appellée par la fonction \texttt{toCExpr} après avoir déplié tous les \texttt{Pi} et \texttt{Lam}, 
il nous suffit de seulement traiter les variables, les sortes, les niveaux d'univers, les constructeurs et les définitions.
Pour rappel, les \texttt{CSpine} sont constitués d'un symbole de tête (représenté par une chaîne de caractères) et d'une liste d'arguments (liste de \texttt{CExpr}).

\paragraph{Les variables.}
Dans la syntaxe interne de Agda, une variable est représentée par un indice de De Bruijn et une liste d'éliminateurs.
Ayant restreint les éliminateurs aux applications pour le moment, nous obtenons un terme déjà très proche d'une spine.
Il nous suffit donc de convertir la liste d'éliminateurs en transformant chaque terme de la liste en \texttt{CExpr}, 
puis de construire la spine en mettant le nom associé à l'indice de De Bruijn avec les arguments convertis.

\paragraph{Les définitions et constructeurs.}
Les termes \texttt{Def} correspondent aux symboles étant rattachés à une définition comme les axiomes (introduits avec le mot clé \textit{postulate} en Agda), 
les fonctions définies par l'utilisateur, les fonctions primitives ou encore les datatypes.
Pour le moment notre prototype ne gère pleinement que les cas ou la définition correspond à un datatype ou un constructeur, 
cependant nous pensons que la technique présentée peut-être facilement adaptée pour gérer les autres cas.

Lorsque l'en rencontre un symbole correspondant à un datatype, 
on récupère le terme correspondant au type de ce datatype et on ajoute au contexte une déclaration contenant le symbole et le terme converti en CExpr.
On récupère par la suite la liste des constructeurs associés à ce datatype et on les ajoute également au contexte via un procédé similaire.

Si on voulait convertir un symbole possédant une définition (comme une fonction définie par l'utilisateur), 
il suffirait de récupérer les différentes clauses de cette fonction et de les convertir en \texttt{CEquations}.
N'ayant pas effectué cette implémentation pour le moment, nous ne détaillerons pas plus ce procédé.

\paragraph{Les univers et leurs niveaux.}
Comme indiqué dans \cite{norman2025canonical}, Canonical ne gère pas les niveaux d'univers.
Nous fournissons donc simplement à Canonical un objet \textbf{Type} ne possédant pas de type dans son contexte.
De cette manière, Canonical n'essaiera pas de typer les éléments de type \texttt{Type} et n'utiliseras pas \texttt{Type} pour construire ses termes.

\section{Cubical Agda}
Maintenant que nous avons un prototype pour les fonctions basiques de Agda, 
nous nous intéressons à son application pour la théorie cubique des types.

\paragraph{Le type intervalle.}
La première étape vers l'utilisation de Canonical pour la théorie cubique des types est le support de l'algèbre de De Morgan libre de l'intervalle.
Nous ajoutons au contexte que nous fournissons à Canonical trois déclarations $\mathsf{(I : \_)}$, $\mathsf{(i0 : I)}$ et $\mathsf{(i1 : I)}$, 
représentant respectivement le type intervalle, l'élément \texttt{0} et l'élément \texttt{1}. 

Nous ajoutons également des déclarations pour les fonctions suivantes :
\begin{itemize}
  \item $\mathsf{(primINeg : I \to I)}$
    \begin{itemize}
      \item $\mathsf{primINeg~i0 = i1}$ 
      \item $\mathsf{primINeg~i1 = i0}$
      \item $\mathsf{primINeg~(primIMax~i~j) = primIMin~(primINeg~i)~(primINeg~j)}$ 
      \item $\mathsf{primINeg~(primIMin~i~j) = primIMax~(primINeg~i) (primINeg~j)}$ 
    \end{itemize}
  \item $\mathsf{(primIMin : I \to I \to I)}$
    \begin{itemize}
      \item $\mathsf{primIMin~i0~j = i0}$ 
      \item $\mathsf{primIMin~i1~j = j}$ 
      \item $\mathsf{primIMin~j~i0 = i0} $
      \item $\mathsf{primIMin~j~i1 = j}$ 
    \end{itemize}
  \item $\mathsf{(primIMax : I \to I \to I)}$
    \begin{itemize}
      \item $\mathsf{primIMax~i0~j = j}$ 
      \item $\mathsf{primIMax~i1~j = i1}$ 
      \item $\mathsf{primIMax~j~i0 = j} $
      \item $\mathsf{primIMax~j~i1 = i1}$ 
    \end{itemize}
\end{itemize}
Comme leurs noms l'indiquent, ces fonctions représentent la négation, le max et le min sur l'intervalle.
À présent que nous avons une représentation du type intervalle, 
nous nous intéressons à la gestion des types d'égalité (aussi appelé path type dans CTT).

\subsection{Représentation des path types}
La première voie que nous avons explorée pour représenter les path type passe par l'utilisation d'un constructeur et
d'un destructeur pour les path type.
Pour ce faire, nous ajoutons au contexte de Canonical un constructeur
\[
\mathsf{makePath} :
(\ell : Level) \to
(A : Type\ \ell) \to
(x : A) \to
(y : A) \to
(p : I \to A)
\{p~i0 = x; p~i1 = y\}
\to x \equiv y
\]
ainsi qu'un destructeur
\[
\mathsf{destructPath} :
(\ell : Level) \to
(A : Type\ \ell) \to
(x : A) \to
(y : A) \to
(p : x \equiv y) \to
(i : I) \to A
\]
avec les règles de réduction :
\[
\begin{aligned}
\mathsf{destructPath}\ \ell\ A\ x\ y\ p\ i0 &= x,\
\mathsf{destructPath}\ \ell\ A\ x\ y\ p\ i1 &= y.
\end{aligned}
\]

Le constructeur sert à contraindre Canonical à fournir une fonction $\mathsf{p : I \to A}$ ayant les bonnes extrémités comme témoin pour justifier une égalité, 
tandis que le destructeur sert à imiter le comportement d'un path type.

Bien que cette approche fonctionne sur des cas simples, celle-ci a rapidement montré ses limites face à des obligations de preuve plus complexes.
En plus d'alourdir fortement les preuves produites par Canonical, 
l'ajout des constructeurs et destructeurs augmente la taille de l'arbre de recherche de termes de Canonical. 
Nous avons donc choisi d'adopter une représentation plus proche de l'utilisation réelle des types de chemins.

La deuxième solution que nous avons adoptée consiste à remplacer toutes les occurrences du type $\mathsf{x \equiv y}$ par le type $\mathsf{I \to A}$, 
et à utiliser les contraintes natives de Canonical pour spécifier le comportement de la fonction aux extrémités de l'intervalle.
Par exemple, un objet $\mathsf{(p : x \equiv y)}$ devient une fonction $\mathsf{(p : I \to A)}$ accompagnée des contraintes $\mathsf{p~i0 = x}$ et $\mathsf{p~i1 = y}$.

\subsection{Contraintes de cohérence.}
Lorsqu'on travaille en théorie cubique des types, un enjeu majeur réside dans la gestion des contraintes imposées aux termes sur les extrémités de l'intervalle.

Par exemple, intéressons-nous à la preuve de l'extensionnalité des fonctions. Cet énoncé, prouvable en théorie cubique des types, stipule que deux fonctions égales point par point sont égales au sein du type des fonctions.

Pour prouver une égalité entre deux fonctions $\mathsf{(f~g : A \to B)}$ en CTT, 
il faut fournir une fonction $\mathsf{(h : I \to (A \to B))}$ telle que $\mathsf{h~i0 = f}$ et $\mathsf{h~i1 = g}$.
En introduisant une variable $\mathsf{(a : A)}$, cela revient à imposer les contraintes $\mathsf{h~i0~a = f~a}$ et $\mathsf{h~i1~a = g~a}$.

Nous présentons en figure \ref{fig:agda-fe} un type décrivant l'extensionnalité des fonctions en Agda.
Comme toutes les variables ont été introduites, le type du but est simplement $\mathsf{B}$.
Si l'on fournit tel quel le but à Canonical, celui-ci n'a aucune connaissance des contraintes que nous venons d'évoquer.

\centering
\begin{minted}[escapeinside=||, mathescape]{agda}
fe : (A B : Type) |$\to$| (f g : A |$\to$| B) |$\to$| (p : (a : A) |$\to$| f a |$\equiv$| g a) |$\to$| f |$\equiv$| g
fe A B f g p i a = { }0
\end{minted}
\caption{Définition du type de l'extensionnalité des fonctions. }
\label{fig:agda-fe}
\end{figure}

Pour palier ce problème, nous nous servons directement d'une fonctionnalité d'Agda.
Dans un tel but, Agda calcule les contraintes que nous avons mentionnées et les affiches à l'utilisateur.
En reprenant l'exemple de la figure \ref{fig:agda-fe}, Agda affiche à l'utilisateur $\mathsf{(i = i0) \vdash f~a}$ et $\mathsf{(i = i1) \vdash g~a}$.
En l'état, il n'est pas possible de spécifier à Canonical de telles contraintes.
La solution que nous avons adoptée est de replier sur le but les éléments du contexte courant jusqu'à la variable d'intervalle qui nous intéresse et à spécifier les contraintes directement sur la déclaration du but.
Le but 0 de la figure \ref{fig:agda-fe} passerais de $\mathsf{(Goal : B)}$ à $\mathsf{(Goal : I \to A \to B)}$ avec les contraintes $\mathsf{Goal~i0~a = f~a}$ et $\mathsf{Goal~i1~a = g~a}$.
Pour revenir au but initial, il suffit de re-déplier le terme fourni par Canonical en se débarrassant des abstractions que nous avons ajouté.


\subsection{La composition homogène avec Canonical}
Comme mentionné lors de notre présentation des la théorie cubique des types, la composition homogène est un élément central pour la construction d'égalités. 
Nous souhaitons fournir à Canonical la possibilité de créer des chemins avec la composition homogène.
Notre première approche était de fournir à Canonical toute la signature de l'implémentation de cet opérateur dans Agda, 
qui est décrit en section 3.3 et 3.4 de \cite{vezzosi2019cubical}.

Nous avons testé cette approche pour prouver la transitivité des chemins et Canonical n'a fourni un résultat qu'au bout de plusieurs minutes.
De plus, la cohérence des faces n'était pas respectée dans le résultat qu'il a fourni.
Cela s'explique par le fait qu'Agda fasse ses vérifications en interne et pas seulement au niveau du type-checker,
la signature seule de l'implémentation n'était donc pas suffisante.

\paragraph{Solution partielle.}
Pour le moment, nous n'avons pas trouvé de moyen de fournir à Canonical la signature complète de \texttt{hcomp}, accompagnée des contraintes sur ses faces.
Nous avons donc essayé d'utiliser Canonical non plus pour trouver l'intégralité de la solution, 
mais comme une aide pour déterminer les faces respectant ces contraintes.
Prenons l'exemple présenté en figure \ref{fig:agda-trans}. 
Ici, les buts \texttt{0} et \texttt{1} doivent contenir les faces gauche et droite que nous avons décrites en figure \ref{fig:hcomp}.
En appliquant la technique de repli dont nous avons discuté dans la section 3.2, 
nous parvenons à fournir à Canonical l'ensemble des contraintes dont il a besoin, et celui-ci fournit alors un résultat satisfaisant.

Par exemple, le but \texttt{1} à comme contraintes $\mathsf{j = i0 \vdash y}$ et $\mathsf{j = i1 \vdash z}$ et comme type $\mathsf{A}$.
En repliant $\mathsf{j}$ sur le goal, on obtient comme but $\mathsf{\Pi (j : I) \to A}$ avec comme contraintes $\mathsf{Goal~i0 = y}$ et $\mathsf{Goal~i1 = z}$.
Canonical nous fourni donc le terme $\mathsf{q~j}$.

\begin{figure}[h]
\centering
\begin{minted}[escapeinside=||, mathescape]{agda}

  trans |$\ell$| A x y z p q i = 
    hcomp {|$\ell$|} {A} {~ i |$\vee$| i} (|$\lambda$| j |$\to$| |$\lambda$| {(i = i0) |$\to$| { }0
                                     ;(i = i1) |$\to$| { }1}) (p i)
\end{minted}
\caption{Preuve incomplète de la transitivité des chemins en Cubical Agda}
\label{fig:agda-trans}
\end{figure}

\paragraph{Limites de l'approche.}
Bien que cette approche fonctionne pour des cas simples, comme celui de la transitivité, 
elle se retrouve bloquée lorsque les cas deviennent plus complexes.
Le cas de la transitivité fonctionne bien, 
car fournir tous les arguments implicites ainsi que la face inférieure à \texttt{hcomp} 
permet à Agda de déduire l'ensemble des contraintes correspondant aux faces qui nous manquent.
Cependant, si la contrainte associée à une face dépend d'une autre face qui n'a pas encore été spécifiée, 
Agda ne peut pas déduire cette contrainte et laisse une méta-variable à la place.
En figure \ref{fig:agda-hard}, les buts \texttt{0} et \texttt{1} sont interdépendants, et notre approche ne permet donc pas de traiter ce cas.

\paragraph{Résultats.}
% L'approche que nous avons présentée au cours de cette section a permis d'automatiser la recherche de plusieurs buts simples.
La ou Mimer n'était pas en capacité de fournir de preuves utilisant la théorie cubique des types, 
notre approche a permis d'automatiser plusieurs preuves simples comme celles des buts présent en figures \ref{fig:agda-fe} et \ref{fig:agda-trans}.
Nous pensons que l'utilisation de Canonical présente un réel potentiel pour l'automatisation de preuves au sein de la théorie cubique des types.

\section{Conclusion et travaux futurs}
Nous rappelons ici ce qui est présenté dans la sous-section éponyme présente au début de ce rapport.

Le travail réalisé au cours de ce stage constitue une preuve de concept pour l’automatisation de la recherche de preuves en théorie cubique des types.
Nous y proposons deux contributions principales. 
La première consiste en une intégration partielle du logiciel de recherche de preuves Canonical au sein de l’assistant de preuves Agda. 
Nous nous sommes intéressés à la conversion des types d’Agda, représentés selon leur syntaxe interne, 
afin de pouvoir fournir des buts à Canonical via sa couche de compatibilité.
Dans un second temps, nous nous sommes appuyés sur l’intégration présentée dans la première partie afin d’automatiser certaines preuves en théorie cubique des types. 
Cette automatisation repose sur un encodage des types de chemins et des contraintes de cohérence associées à leurs extrémités.

Dans le cadre de travaux futurs, nous souhaiterions dans un premier temps améliorer l’utilisabilité de Canonical au sein d’Agda. 
Cela passerait notamment par la possibilité de récupérer automatiquement les définitions de fonctions afin de les transformer en équations qui seraient ensuite fournies à Canonical, 
par la gestion du pattern matching d’Agda, ainsi que par différentes corrections de bugs et améliorations de l’interface utilisateur.

Dans un second temps, nous souhaiterions poursuivre l’étude des différentes manières d’encoder la théorie cubique des types et ses spécificités au sein d’autres théories des types, 
telles que celle utilisée par Canonical.
Cette voie constitue l’une des pistes que nous explorerons dans le cadre de ma thèse, 
qui a pour objectif de rendre plus efficace l’évaluation des preuves en théorie homotopique et cubique des types.

toCExpr :: Term ->           -- ^ Le terme a convertir
           [String] ->       -- ^ Variables liees
           [CDecl] ->        -- ^ Parametres
           [CDecl] ->        -- ^ Contexte
           Map String Bool -> -- ^ Définitions déjà rencontrées
           Bool ->           -- ^ En train de convertir le Goal ?
           Bool ->           -- ^ En train de convertir vers un type ?
           TCM (CExpr, [CDecl], Map String Bool)
toCExpr t bindnames pidecl letdecl ald tplvl totyp =
  case t of
    Pi a b -> do
      (newnames, na) <- do case b of
                            NoAbs _ _ -> return (bindnames, "_")
                            Abs n _ -> do
                              n' <- freshString n
                              return (n' : bindnames, n')
      (domdecl, lets, ald) <- toCDecl (unEl $ unDom a) na [] bindnames letdecl ald False
      toCExpr (unEl $ unAbs b) newnames (domdecl : pidecl) lets ald tplvl totyp
    Lam a b -> do
      let (newnames, name) = case b of
                      NoAbs _ _ -> (bindnames, "_")
                      Abs n _ -> (n : bindnames, n)
      toCExpr (unAbs b) newnames (CDecl name Nothing [] : pidecl ) letdecl ald tplvl False
    _ -> do
      (spine, lets, ald) <- toCSpine t bindnames letdecl ald
      return $ (
        CExpr {
            params = reverse pidecl,
            lets = if tplvl then reverse lets else [],
            spine
          }, lets, ald)
\end{minted}

            [String] ->       -- ^ Les variables liées

toCSpine t bindnames lets ald =
  case t of
    Var i el -> do
      (args, lets, ald) <- elimsToCExpr el bindnames lets ald
      return $ ( CSpine (bindnames !! i) args, lets, ald)
    Sort (Type l) -> do
      t' <- reallyUnLevelView l
      (arg, lets, ald) <- toCExpr t' bindnames [] lets ald False False
      return $ (
        CSpine {
          head = "Type",
          args = [arg]
        }, lets, ald)
    Level l -> do
      t' <- reallyUnLevelView l
      toCSpine t' bindnames lets ald
    Def qname e -> do
      (args, lets, ald) <- elimsToCExpr e bindnames lets ald
      (lets, ald) <- gatherDatatypeInformations qname bindnames lets ald
      return $ (
        CSpine {
          head = P.prettyShow (qnameName qname),
          args
        }, lets, ald)
    Con hd _ e -> do
      infos <- getConstInfo (conName hd)
      let dataname = case theDef infos of
                    ConstructorDefn cd -> _conData cd
                    _ -> __IMPOSSIBLE__
      (args, lets, ald) <- elimsToCExpr e bindnames lets ald
      (lets, ald) <- gatherDatatypeInformations dataname bindnames lets ald
      return $ (
        CSpine {
          head = P.prettyShow . qnameName $ conName hd,
          args
        }, lets, ald)
