\subsection*{Contexte général} 
Les assistants de preuves sont des logiciels permettant de formaliser des résultats mathématiques et 
ainsi d'aider leurs utilisateurs à rédiger des preuves correctes. 
Certains assistants de preuves, tels que Rocq \cite{rocq}, Lean \cite{demoura2021lean4} ou Agda \cite{norell2008agda}, 
s'appuient sur la théorie des types dépendants pour représenter les énoncés mathématiques et leurs preuves.
Au sein de ces systèmes, un énoncé est représenté par un type, tandis qu'une preuve est représentée par un terme habitant ce type.
Le problème de l'habitation des types constitue donc un enjeu majeur dans le domaine de la formalisation automatisée.

Canonical \cite{norman2025canonical} est un logiciel de recherche de preuve 
se basant sur une théorie des types dépendants dont le format est optimisé pour la recherche de termes.
Son intégration dans l’assistant de preuve Lean a montré que cette approche 
s’intègre particulièrement bien aux assistants de preuves fondés sur la théorie des types dépendants. 
Elle présente notamment des performances supérieures à celles des autres logiciels de recherche de preuves disponibles dans Lean.

\subsection{La théorie des types dépendants.}

\paragraph{Un système de preuves.}
Une théorie des types est un système formel dans lequel on s’intéresse notamment aux programmes bien typés. 
Celle-ci est définie par un ensemble de termes (programmes) constructibles, un ensemble de types constructibles, 
ainsi qu’un ensemble de règles de typage permettant d’attribuer des types aux termes et de définir les conversions entre types.
Nous notons $\mathsf{t : T}$ pour indiquer qu'un terme $\mathsf{t}$ est de type $\mathsf{T}$ et $\mathsf{\Gamma \vdash t : T}$ 
que le contexte $\mathsf{\Gamma}$ permet de déduire que $\mathsf{t}$ est de type $\mathsf{T}$.

\paragraph{Correspondance de Curry-Howard.}
Dans ses travaux \cite{howard1980formulae}, Howard établit un lien profond entre les propositions de la logique intuitionniste et les types.
Via cette correspondance, prouver qu'une formule $\mathsf{A}$ est vraie revient à exhiber un programme construisant un objet de type $\mathsf{A}$.
En enrichissant nos types en permettant aux types de dépendre de termes, 
on obtient un système de preuves dans lequel on peut décrire tous les énoncés mathématiques, la théorie des types dépendants \cite{martinlof1984intuitionistic}.

\paragraph{Assistants à la preuve.}
Les assistants à la preuve comme Rocq, Lean et Agda sont basés sur des théories des types dépendants.
Dans ces systèmes, on décrit un énoncé à prouver via un type, et une preuve de cet énoncé via un terme qui à le type correspondant. 
L'assistant vérifie que le terme possède le bon type avec un algorithme de type-checking \cite{coquand1996algorithm}. 
Dans la figure \ref{fig:agda-proof}, la première ligne permet de spécifier le type (l'énoncé) à prouver, 
et la deuxième décrit un terme (une preuve) de ce type dans la syntaxe d'Agda\footnote{Le manuel de référence d'Agda : \url{https://agda.readthedocs.io/en/latest/}}.

\subsection{La théorie cubique des types}
\subsubsection{La théorie homotopique des types.}
En mathématiques, on étudie souvent des objets à travers différentes représentations. 
Cependant, les propriétés intrinsèques de ces objets ne dépendent pas de la représentation choisie. 
Par exemple, un graphe peut être étudié à travers sa liste d’adjacence ou sa matrice d’adjacence.

C’est dans le but de formaliser cette indépendance vis-à-vis de la représentation que l’axiome d’univalence a été introduit par Voevodsky. 
Celui-ci stipule que, pour deux types, l’existence d’une équivalence entre ceux-ci est liée à l’existence d’une égalité entre ces deux types. 
Une équivalence peut être vue comme une manière de mettre en correspondance deux types tout en préservant leur structure.

Cet axiome constitue le principal ajout de la théorie homotopique des types \cite{hottbook} (HoTT). 
Celle-ci possède de nombreuses propriétés. 
Du point de vue du mathématicien, cette théorie se présente comme une alternative à la théorie des ensembles, 
tout en offrant des outils puissants pour développer l’homotopie synthétique. 
L’extensionnalité des fonctions et des propositions est également démontrable dans cette théorie.

Cependant, l’ajout de l’axiome d’univalence brisent les propriétés calculatoires de la théorie des types, 
car aucune règle de calcul ne lui est associée.

\subsubsection{Une interprétation constructive de l'univalence.}
Dans le but de retrouver ces propriétés calculatoires, la théorie cubique des types \cite{cohen2016cubical} a été introduite par Cohen, Coquand, Huber et Mörtberg.
Celle-ci ajoute un nouveau type $\mathsf{I}$ représentant l’intervalle $\mathsf{[0;1]}$ et donne une nouvelle interprétation de l’égalité.
Une preuve d’égalité entre deux termes $\mathsf{x}$ et $\mathsf{y}$ d’un type $\mathsf{A}$ est interprétée comme une fonction de l’intervalle vers le type $\mathsf{A}$ qui,
lorsqu’elle est évaluée en $\mathsf{0}$ (respectivement $\mathsf{1}$), doit être définitionnellement égale à $\mathsf{x}$ (respectivement $\mathsf{y}$).

Picturalement, une égalité en théorie cubique des types peut être représentée comme une arête,
une égalité entre égalités (une fonction de $\mathsf{I \times I \to A}$) comme un carré,
et une fonction de $\mathsf{I \times I \times I \to A}$ comme un cube, et ainsi de suite.

\subsubsection{La composition homogène}
Un autre ingrédient clé de la théorie cubique des types est l’opérateur de composition homogène.
Introduit dans le CCHM \cite{cohen2016cubical}, cet opérateur permet de compléter des cubes ouverts en dimension $\mathsf{n}$.
Pour cela, il suffit de lui spécifier un ensemble de faces cohérentes entre elles, ainsi qu’une base permettant de construire la face manquante.

Par exemple, dans la figure \ref{fig:hcomp}, les faces de gauche, de droite et du bas ont été fournies à l’opérateur $\mathsf{hcomp}$,
qui construit alors la face du haut.
Comme mentionné précédemment, pour que cet opérateur fonctionne, les faces fournies doivent être cohérentes aux endroits où elles se rencontrent.
Supposons que $\mathsf{i = i0}$ et $\mathsf{j = i0}$, correspondant au coin en bas à gauche.
Les deux arêtes qui se rencontrent doivent alors désigner un même terme, ici $\mathsf{a}$.

\subsection{La preuve automatisée en théorie cubique des types.}
Un enjeu majeur de la théorie cubique des types est de parvenir à automatiser la recherche de preuves. 
Dans les théories des types dépendants plus classiques, il existe plusieurs classes d’outils permettant d’automatiser cette recherche.

Une première classe d’outils regroupe ceux qui cherchent à appliquer automatiquement des tactiques. 
On peut notamment citer Aesop \cite{limpberg2023aesop} dans Lean, ainsi que les nombreuses tactiques de Rocq permettant d’effectuer ce type de recherche, 
telles que \texttt{tauto} ou \texttt{firstorder}.

Une deuxième classe de prouveurs automatiques traduit les obligations de preuve dans une logique du premier ordre. 
C’est notamment le cas de Coqhammer \cite{czajka2018hammer} dans Rocq et de Sledgehammer \cite{bohme2010sledgehammer} dans Isabelle, 
qui transmettent ensuite les formules obtenues à des solveurs SMT ou des prouveurs automatiques tels que Vampire \cite{bartek2025vampire}, 
CVC5 \cite{barbosa2022cvc5} ou Z3 \cite{de2008z3}.

Enfin, une dernière classe regroupe les logiciels reposant directement sur l'habitation de types. 
C’est notamment le cas d’Agsy et de son successeur Mimer \cite{skystedt2022new} dans Agda.

À notre connaissance, aucune de ces approches n’est actuellement utilisée pour l’automatisation de la recherche de preuves en théorie cubique des types.

\section{Traduction d'Agda vers Canonical}
Dans cette section, nous présentons l’intégration de Canonical au sein d’Agda. 
Nous introduisons dans un premier temps Canonical, puis la solution étudiée pour permettre son utilisation depuis Agda. 
Nous terminons par la présentation de la méthode utilisée pour convertir les types d’Agda en types de Canonical.

\subsection{Canonical}
Canonical est un solveur pour les théories des types dépendants écrit en Rust par Norman et Avigad \cite{norman2025canonical}.
Celui-ci fonctionne sur sa propre théorie des types ce qui lui permet, entre autre, 
d'être totalement indépendant des assistants de preuves et de pouvoir potentiellement être utilisé avec plusieurs assistants.
Il suffit de l'ajouter comme un plugin et de transformer les énoncés de l'assistant à la preuve en types de Canonical,
les lui fournir pour qu'il effectue sa recherche de preuves et, en cas de succès, traduire le résultat dans le langage de l'assistant à la preuve.
Dans leurs travaux \cite{norman2025canonical}, Norman et Avigad présentent une telle implémentation de Canonical dans l'assistant à la preuve Lean. 

\paragraph{Fonctionnement.} 
Étant donné un type, Canonical essaie de trouver un terme qui habite ce type en effectuant une recherche exhaustive en profondeur sur les termes.
Le problème de l'habitation de type en théorie des types dépendants étant indécidable,
Canonical n'est pas garanti de trouver un résultat au problème qui lui est posé.
Son implémentation en Lean a cependant montré des performances accrue face à celle de Aesop et Duper.
Nous avons donc décidé d'utiliser Canonical pour notre prototype en vue de l'utiliser pour la théorie cubique des types.

\paragraph{Théorie des types.}
Afin de pouvoir restreindre au maximum son arbre de recherche tout en gardant maximum d'expressivité, 
Canonical fonctionne sur sa propre théorie des types que nous donnons en figure \ref{fig:canonical-tt}.
Celle-ci possède un unique constructeur de termes composé d'une liste de parametres, d'une liste de déclaration let, 
un symbole de tête et une liste d'arguments.
Un type de Canonical est un terme qui possède des annotations de types sur les lieurs (let et $\lambda$).

Chaque terme de Canonical doit être sous forme $\beta$-normale (aucune $\beta$-réduction au sein du terme) 
et tout symbole d'arité $n$ doit être appliqué à exactement $n$ arguments (quitte à $\eta$-étendre les fonctions).
Le symbole de tête du terme doit être lié par un let ou une $\lambda$-abstraction.

Au sein des types, chaque annotation de type est entièrement optionnel.
Un symbole dont le type n'est pas spécifié indique à Canonical que le symbole ne devrait pas être utilisé pour construire le terme Goal.

\paragraph{Appel à Canonical.}
Dans le but d'aider l'utilisateur à remplir le goal dans lequel il se trouve, 
nous souhaitons implémenter une commande qui récupère le type du goal courant et le fourni à Canonical.
Deux solutions ont été envisagées afin de répondre à cette problématique.
La première solution est de passer par le langage de reflection de Agda. 
Celui-ci permet d'écrire des tactics de résolution directement comme des termes d'Agda.
La deuxième solution consiste à implémenter une fonction d'appel à Canonical directement dans l'assistant lui-même dans son code Haskell.
Nous récupèrons les types des goals écrit dans la syntaxe interne des termes d'Agda puis, après une passe de transformation, 
envoyons le type de goal à Canonical via la FFI de Haskell.
Étant la solution en partie utilisée par Mimer et pour des raisons d'ergonomie, nous avons choisi de nous concentrer sur la deuxième solution.

\subsection{Cibles de la traduction}
La théorie des types de Agda étant différente de celle de Lean, 
nous devons adapter les techniques présentées dans \cite{norman2025canonical} pour faire notre traduction.

\paragraph{Les termes.}
Les termes sont composés des variables (indices de de Bruijn), potentiellement appliqués à divers arguments, des $\lambda$-abstractions, 
ainsi que du type des fonctions dépendantes.

Ils sont également composés des définitions (noms de fonctions, noms de datatype, etc.) et des constructeurs, pouvant aussi être appliqués à divers arguments.

Enfin, les termes contiennent également les sortes et les niveaux d'univers.

Dans la syntaxe réelle, les termes contiennent également d'autres constructions que nous n'aborderons pas dans ce travail.

\paragraph{Les éliminateurs.}
Au sein d'Agda, le type des éliminateurs permettent de représenter les applications de fonctions, les projections (types enregistrements) et les applications de chemin cubiques.
Pour le moment, nous ne nous interessons qu'aux applications.


\paragraph{Les sortes et types d'univers.}
Pour ce stage, nous avons choisi de restreindre notre prototype qu'aux sortes en liens avec les petits univers et leurs niveaux.
Nous expliquons ce choix par le fait que la majorité des cas testé ne présentaient pas de sortes autres que celles-ci.
De plus, au vue de la gestion des univers par Canonical (que nous détaillerons par la suite), 
ajouter du support pour les autres construction ne ferait qu'ajouter du bruit à la recherche de terme.



\subsubsection{La cible.}
Canonical est fourni avec une couche de compatibilité permettant de faire le lien avec le coeur du prouver tout en gardant une syntaxe plus agréable à utiliser.
La figure \ref{fig:can-comp} montre la syntaxe pour représenter les termes et les types au sein de la couche de compatibilité en syntaxe Haskell.

\paragraph{CDecl.}
Ce type décrit les déclaration de la forme $(x : A)$.
Il est composé d'un symbole, optionnellement d'un type et d'équations.

Si le champs typ n'est pas renseigné, cela peut signifier deux choses : 
Dans le cas d'une déclaration let, ça indique à Canonical que le symbole ne devrait pas être utilisé pour construire le résultat.
Dans le cas d'un paramettre, que l'expression a laquelle la déclaration appartient représente un terme et non pas un type.

Les équations associées aux déclarations ont une interprétation qui dépendant également du champ auquel les déclarations sont associées : 
Dans le cas d'une déclaration let, les équations représentent les règles de réductions associées au symbole (e.g. définition de fonction).
Dans le cas d'un paramètre, elles représentent des contraintes de réduction sur ce parametre.

\paragraph{CEquation.}
Ce type représente une règle de la forme $lhs = rhs$ à travers deux spines.
Par exemple, la déclaration associée à la fonction $not : Bool \to Bool$, définie par $not~True = False$ et $not~False = True$,
possèdera deux équations dont les membres de gauche seront $CSpine~"not"~[trueExpr]$ (resp. $CSpine~"not"~[falseExpr]$) et les membres de droites seront
$CSpine~"False"~[]$ (resp. $CSpine~"True"~[]$). 


\paragraph{CExpr.}
Ce type représente à la fois les termes et les types de Canonical que nous avons introduit en sous-section 2.1.
La distinction entre des termes et des types se voit au sein des champs params et lets. 
Contrairement aux types, un terme ne possèderas pas d'annotations de types dans ses champs.

\paragraph{CSpine.}
Les spines sont composées d'un symbole de tête et d'une liste d'arguments. 
Elles représentent le corps des types / termes de Canonical.

\subsection{La traduction.}
Maintenant que nous avons vu le langage source et la cible, interessons nous à la traduction en elle-même.
Notre traduction se découpe en trois fonctions mutuellement récursives pemettant de transformer des termes en déclaration $toCDecl$, en expression $toCExpr$ ou en spine $toCSpine$.

\paragraph{Le point d'entrée.}
Canonical attend pour son Goal une déclaration, notre point d'entrée est donc la fonction toCDecl dont l'implémentation en Haskell est présentée en figure \ref{fig:agda-toCDecl}.
Celle-ci va simplement prendre un nom, un terme à convertir et un ensemble d'équations, 
appeler la fonction toCExpr sur le terme à convertir et créer la structure CDecl correspondante.
Les autres arguments de la fonction servent pour des processus que nous détaillerons plus tard.



\begin{figure}[h]
\centering
\begin{minted}{haskell}

           String -> -- ^ Le nom associé à la déclaration
           [CEquation] -> -- ^ Les contraintes / définitions
           [String] -> -- ^ Nom liés
           [CDecl] -> -- ^ Contexte
           Map String Bool -> -- ^ Définitions déjà rencontrées
           Bool -> -- ^ En train de transformer la déclaration "Goal"?
           TCM (CDecl, [CDecl], Map String Bool)
toCDecl t name eqs bindnames lets ald tplvl = do
  toCExpr t bindnames [] lets ald tplvl True
\end{minted}
\caption{Traduction des termes en CDecl.}
\label{fig:agda-toCDecl}
\end{figure}

\subsubsection{Conversion en termes de Canonical}
La fonction toCExpr a pour but premier de créer la liste de parametre qu'il y a dans un terme / type de Canonical.
Pour ce faire, la fonction parcours le terme en gardant en mémoire les paramètres créés jusqu'à ce qu'elle rencontre un terme qui ne créé pas de paramètres.

\paragraph{Termes créant des paramètres.}
Il y deux constructeurs qui se traduisent en termes de Canonical : Lam et Pi.
Dans le cas de Lam, il suffit d'ajouter une déclaration contenant seulement le nom de la variable à la liste des paramètres et de s'appeler récursivement sur le terme sous jacent.
Dans le cas de Pi, il faut distinguer deux cas : 
Si nous sommes en train de convertir le terme vers un type, il suffit de convertir le domaine du Pi vers une CDecl, 
de l'ajouter au paramètres et d'appeler récursivement toCExpr sur le codomaine.
Si nous sommes en train de convertir vers un terme, il faut traduire le termes avec le procédé décrit dans la section 4.1 de \cite{norman2025canonical}.
Cette fonctionnalité n'a pas encore été implémentée dans notre prototype.
La distinction entre traduction vers termes ou type se fait en fonction de la fonction appelant toCExpr : 
Si c'est toCDecl qui l'appelle, cela signifie que nous somme en train de convertir effectivement un type.
Dans le cas contraire, c'est que la fonction a été appelée par toCSpine et que nous sommes en train de convertir des arguments de fonctions, donc des termes.

\paragraph{Autres constructeurs.}
Dans le cas ou toCExpr est appelé sur d'autre constructeur que Pi et Lam, cela signifie que tous les paramètres ont été dépliés.
Il faut donc convertir le termes vers une spine (constructeur de tête et arguments) et créer la CExpr en mettant les paramètres avec la spine.

Un point que nous n'avons pas encore abordé concerne la gestion du contexte du Goal.
Celui-ci sert à mettre tout ce qui est en lien avec les constantes, les fonctions externes, les datatypes et les constructeurs.
Notre stratégie consite à mettre tout cet environnement sur l'expression correspondant au type du goal. 
L'environnement se construisant tout au long de la conversion du terme, nous devons le garder en mémoire et l'ajouter qu'à la toute fin de la traduction,
après avoir converti la spine du goal.
Nous détaillerons la construction de l'environnement par la suite.

\subsubsection{Conversion en spine.}
La fonction toCSpine sert à convertir les termes de Agda vers un symboles de tête et ses potentiels arguments.
Étant seulement appellée par la fonction toCExpr après avoir déplié tous les Pi et Lam, il nous suffit de seulement traiter les variables, les sortes, les niveaux d'univers, les constructeurs et les définitions.
Pour rappel, les CSpine sont constitué d'un symboles de tête (représenté par une chaîne de caractères) et d'une liste d'arguments (liste de CExpr).

\paragraph{Les variables.}
Dans la syntaxe interne de Agda, une variable est représentée par un indice de de Bruijn et une liste d'éliminateurs.
Ayant restreints les éliminateurs aux applications pour le moment, nous obtenons un termes déjà très proche d'une spine.
Il nous suffit donc de convertir la liste d'éliminateurs en transformant chaque termes de la liste en CExpr, 
puis de construire la spine en mettant le nom associé à l'indice de de Bruijn avec les arguments convertis.

\paragraph{Les définitions et constructeurs.}
Les termes Def correspondent aux symboles étant rattachés à une définition comme les axiomes (introduits avec le mot clé postulate en Agda), 
les fonctions définies par l'utilisateurs, le fonctions primitive ou encore les datatypes.
Pour le moment notre protoype ne gère pleinement que les cas ou la définition correspond à un datatype ou un constructeurs, 
cependant nous pensons que la technique présenté peut-être facilement adaptée pour gérer les autres cas.

Lorsque l'en rencontre un symbole correspondant a un datatype, 
on récupère le terme correspondant au type de ce datatype et on ajoute au contexte une déclaration contenant le symbole et le termes converti en CExpr.
On récupère par la suite la liste des constructeurs associés à ce datatype et on les ajoutes également au contexte via un procédé similaire.

Si on voulait convertir un symbole possèdant une définition (comme une fonction définie par l'utilisateur), 
il suffirait de récupérer les différentes clauses de cette fonction et de les convertir en CEquations.
N'ayant pas effectuer cette implémentation pour le moment, nous ne détaillerons pas plus ce procédé.

\paragraph{Les univers et leurs niveaux.}
Comme indiqué dans \cite{norman2025canonical}, Canonical ne gère pas les niveaux d'univers.
Nous fournissons donc simplement à Canonical un objet \textbf{Type} ne possèdant pas de type dans son contexte.
De cette manière, Canonical n'essaiera pas de typer les éléments de type Type et n'utiliseras pas Type pour construire ses termes.


\section{Cubical Agda}
Maintenant que nous avons un protoype fonctionnant pour les fonctionnalités basiques de Agda, 
nous nous intéressons à son application pour la théorie cubique des types.

\paragraph{Le type interval.}
La première étape vers l'utilisation de Canonical pour la théorie cubique des types est le support de l'algèbre de de Morgan libre de l'interval.
Nous ajoutons donc au contexte que nous fournissons à Canonical trois déclarations $(I : \_)$, $(i0 : I)$ et $(i1 : I)$, 
représentant respectivement le type interval, l'élément 0 et l'élément 1. 

Nous ajoutons également des déclarations pour les fonctions suivantes :
$(primINeg : I \to I) {primINeg i0 = i1; primINeg i1 = i0; primINeg (primIMax i j) = primIMin (primINeg i) (primINeg j); primINeg (primIMin i j) = primIMax (primINeg i) (primINeg j)}$ 

$(primIMin : I \to I \to I) {primIMin i0 j = i0; primIMin i1 j = j; primIMin j i0 = i0; primIMin j i1 = j}$ 

$(primIMax : I \to I \to I) {primIMax i0 j = j; primIMax i1 j = i1; primIMax j i0 = j; primIMax j i1 = i1}$ 

A présent que nous avons une représentation du type interval, nous nous interessons à la gestion des types d'égalité (aussi appelé path type dans CTT).

\subsection{Représentation des path types}
La première voie que nous avons explorer pour représenter les path type passe par l'utilisation d'un constructeur et d'un destructeur pour les paths type.
Pour ce faire, nous ajoutons au contexte de Canonical un constructeur 
$makePath : (\ell : Level) \to (A : Type \ell) \to (x : A) \to (y : A) \to (p : I \to A){p i0 = x; p i1 = y} \to x \equiv y$ 
ainsi qu'un destructeur 
$destructPath : (\ell : Level) \to (A : Type \ell) \to (x : A) \to (y : A) \to (p : x \equiv y) \to (i : I) \to A$
avec les règles de réduction :
$destructPath \ell A x y p i0 = x$ et 
$destructPath \ell A x y p i1 = y$.

Le constructeur sert a forcer Canonical a fournir une fonction $p : I \to A$ avec les bonnes extrémité comme témoin pour justifier une égalité
et le destructeur sert à imiter le comportement d'un path type.

Bien que cette approche fonctionne sur des cas simple, celle-ci à vite montré ses limites sur des obligations de preuves plus compliquées.
En plus d'alourdir fortement les preuves fournies par Canonical, l'ajout des constructeur et destructeur grossi l'arbre de recherche de termes de Canonical.
Nous avons donc choisi d'adopter une représentation plus proche de l'utilisation réèlle.

La deuxième solution que nous avons adoptée consiste à remplacer tous les occurences du type $x \equiv y$ par le type $I \to A$ 
et d'utiliser les contraintes builtin de Canonical pour spécifier le comportement de la fonction sur les points extrêmes de l'interval.
Par exemple, un objet $(p : x \equiv y)$ deviendra une fonction $(p : I \to A)$ avec comme contraintes $p i0 = x$ et $p i1 = y$.

\subsection{Contraintes de cohérence.}
Lorsqu'on travaille en théorie cubique des types, un enjeu majeur est la contrainte de termes sur les extrémités.
Par exemple, interessons nous à la preuves de l'extensionnalité des fonctions.
Cet énnoncé prouvable en théorie cubique des types dit que deux fonctions égales point par point sont égales (au sein du type des fonctions).

Pour prouver une égalité entre fonctions deux fonctions $(f g : A \to B)$  en CTT, il faut donner une fonction $(h : I \to (A \to B))$ telle que $h i0 = f$ et $h i1 = g$.
En introduisant une variable $(a : A)$, cela revient a donner comme contrainte que $h i0 a = f a$  et $h i1 a = g a$.

Nous montrons en figure \ref{fig:agda-fe} un type décrivant l'extensionnalité des fonctions en Agda. 
Comme toutes les variables ont été introduites, le type du but est simplement $B$. 
Si l'on fourni tel quel le but a Canonical, celui-ci n'a auucne connaisance des contraintes que nous avons évoquées.

\begin{figure}[h]
\centering
\begin{minted}[escapeinside=||, mathescape]{agda}
fe : (A B : Type) |$\to$| (f g : A |$\to$| B) |$\to$| (p : (a : A) |$\to$| f a |$\equiv$| g a) |$\to$| f |$\equiv$| g
fe A B f g p i a = { }0
\end{minted}
\caption{Définition du type de l'extensionnalité des fonctions. }
\label{fig:agda-fe}
\end{figure}

Pour palier a ce problème, nous nous servons directement d'une fonctionnalité d'Agda.
Dans un tel but, Agda calcule les contraintes que nous avons mentionnées et les affiches à l'utilisateur.
En reprenant l'exemple de la figure \ref{fig:agda-fe}, Agda affiche à l'utilisateur $ (i = i0) \vdash f a$ et $(i = i1) \vdash g a$.
En l'état, il n'est pas possible de spécifier à Canonical de telle contraintes.
La solution que nous avons adopté est de replier sur le but les éléments du contexte courant jusqu'à la variable d'interval qui nous interesse et à spécifier les contraintes directement sur la déclaration du goal.
Le but 0 de la figure \ref{fig:agda-fe} passerais de $(Goal : B)$ à $(Goal : I \to A \to B)$ avec les contraintes $Goal i0 a = f a$ et $Goal i1 a = g a$.
Pour revenir au but initial, il suffit de redéplier le termes fourni par canonical en se débarassant des abstraction que nous avons ajouté.


\subsection{La composition homogène avec Canonical}
Nous avons donc chercher un moyen de fournir à Canonical la possibilité de creer des chemins avec la composition homogène.
Notre première approche était de fournir a Canonical toute la signature de l'implémentation de cet opérateur dans Agda, 
qui est décrit en section 3.3 et 3.4 de \cite{vezzosi2019cubical}.

\paragraph{Limites de cette approche.}
Lorsque nous avons tester cette approche pour prouver la transitivité des chemins, 
Canonical n'a fourni un résultat qu'au bout de plusieurs minutes.
La cohérence des faces n'était pas respectée dans le résultat qu'il a fourni.
Cela s'esplique par le fait qu'Agda fasse ses vérifications en interne et pas seulement au niveau du typechecker,
la signature seule de l'implémentation n'était donc pas suffisante.

\paragraph{Solution partielle.}
Pour le moment, nous n'avons pas trouver de moyen pour fournir à Canonical la signature complète de hcomp avec les contraintes de faces.
Nous avons donc essayer d'utiliser Canonical non plus pour trouver l'entièreté de la solution mais comme aide pour trouver les faces respectant les contraintes.
Prenons l'exemple en figure \ref{fig:agda-trans}.
Ici les buts 0 et 1 doivent contenir les faces de gauche et de droite que nous avons décrit en figure \ref{fig:hcomp}.
En appliquant la technique de repli dont nous avons discuté en section 3.2, 
nous arrivons a fournir a Canonical toutes les contraintes dont il a besoin et celui-ci fourni un résultat satisfaisant.

Par exemple, le goal 1 à comme contraintes $j = i0 \vdash y$ et $j = i1 \vdash z$ et comme type $A$.
En repliant $j$ sur le goal on obtient comme but $\Pi (j : I) \to A$ avec comme contraintes $Goal i0 = y$ et $Goal i1 = z$.
On obtient alors de Canonical $q j$.

\paragraph{Limites de l'approche.}
Bien que cet approche fonctionne pour des cas simples comme celui de la transitivité, 
celle-ci se retrouve bloquée lorsque les cas deviennent plus complexes.
Le cas de la transitivité fonctionne bien car fournir tous les arguments au implicite et la face du bas à hcomp permet à Agda 
de déduire toutes les contraintes pour les faces qu'ils nous manque.
Cependant, si une contraintes pour une face dépend d'une autre face pas encore spécifié, Agda ne peut pas déduire la contrainte et laisse une méta-variable à la place.
En figure \ref{fig:agda-hard}, les buts 0 et 1 sont interdépendants et notre approche ne permet pas de l'illuster.

\paragraph{Résultats.}
% L'approche que nous avons présentée au cours de cette section a permis d'automatiser la recherche de plusieurs buts simples.
La ou Mimer n'était pas en capacité de fournir de preuves utilisant la théorie cubique des types, 
notre approche a permis d'automatiser plusieurs preuves simples que nous avons présenté durant cette section.
Nous pensons que l'utilisation de Canonical présente un réel potentiel pour l'automatisation de preuves au sein de la théorie cubique des types.

                 ; (i = i1) |$\to$| q ((~ j) |$\wedge$| k)

\section{Conclusion et travaux futurs}
Nous repètons ici ce qui est présenté dans la sous-section éponyme présente au début de ce rapport.

Le travail réalisé au cours de ce stage constitue une preuve de concept pour l’automatisation de la recherche de preuves en théorie cubique des types.
Nous y proposons deux contributions principales. 
La première consiste en une intégration partielle du logiciel de recherche de preuves Canonical au sein de l’assistant de preuves Agda. 
Nous nous sommes notamment intéressés à la conversion des types d’Agda, représentés selon leur syntaxe interne, 
afin de pouvoir fournir des buts à Canonical via sa couche de compatibilité.
Dans un second temps, nous nous sommes appuyés sur l’intégration présentée dans la première partie afin d’automatiser certaines preuves en théorie cubique des types. 
Cette automatisation repose notamment sur un encodage des types de chemins et des contraintes de cohérence associées à leurs extrémités.

Dans le cadre de travaux futurs, nous souhaiterions dans un premier temps améliorer l’utilisabilité de Canonical au sein d’Agda. 
Cela passerait notamment par la possibilité de récupérer automatiquement les définitions de fonctions afin de les transformer en équations qui seraient ensuite fournies à Canonical, 
par la gestion du pattern matching d’Agda, ainsi que par différentes corrections de bugs et améliorations de l’interface utilisateur.

Dans un second temps, nous souhaiterions poursuivre l’étude des différentes manières d’encoder la théorie cubique des types et ses spécificités au sein d’autres théories des types, 
telles que celle utilisée par Canonical.
Cette voie constitue l’une des pistes que nous explorerons dans le cadre de ma thèse, 
qui a pour objectif de rendre plus efficace l’évaluation des preuves en théorie homotopique et cubique des types.

toCExpr :: Term ->           -- ^ Le terme a convertir
           [String] ->       -- ^ Variables liees
           [CDecl] ->        -- ^ Parametres
           [CDecl] ->        -- ^ Contexte
           Map String Bool -> -- ^ Définitions déjà rencontrées
           Bool ->           -- ^ En train de convertir le Goal ?
           Bool ->           -- ^ En train de convertir vers un type ?
           TCM (CExpr, [CDecl], Map String Bool)
toCExpr t bindnames pidecl letdecl ald tplvl totyp =
  case t of
    Pi a b -> do
      (newnames, na) <- do case b of
                            NoAbs _ _ -> return (bindnames, "_")
                            Abs n _ -> do
                              n' <- freshString n
                              return (n' : bindnames, n')
      (domdecl, lets, ald) <- toCDecl (unEl $ unDom a) na [] bindnames letdecl ald False
      toCExpr (unEl $ unAbs b) newnames (domdecl : pidecl) lets ald tplvl totyp
    Lam a b -> do
      let (newnames, name) = case b of
                      NoAbs _ _ -> (bindnames, "_")
                      Abs n _ -> (n : bindnames, n)
      toCExpr (unAbs b) newnames (CDecl name Nothing [] : pidecl ) letdecl ald tplvl False
    _ -> do
      (spine, lets, ald) <- toCSpine t bindnames letdecl ald
      return $ (
        CExpr {
            params = reverse pidecl,
            lets = if tplvl then reverse lets else [],
            spine
          }, lets, ald)
\end{minted}

toCSpine :: Term ->           -- ^ Le termes à convertir
            [String] ->       -- ^ Les variables liées
            [CDecl] ->        -- ^ Contexte
            Map String Bool -> -- ^ Définitions déjà rencontrées
            TCM (CSpine, [CDecl], Map String Bool)
toCSpine t bindnames lets ald =
  case t of
    Var i el -> do
      (args, lets, ald) <- elimsToCExpr el bindnames lets ald
      return $ ( CSpine (bindnames !! i) args, lets, ald)
    Sort (Type l) -> do
      t' <- reallyUnLevelView l
      (arg, lets, ald) <- toCExpr t' bindnames [] lets ald False False
      return $ (
        CSpine {
          head = "Type",
          args = [arg]
        }, lets, ald)
    Level l -> do
      t' <- reallyUnLevelView l
      toCSpine t' bindnames lets ald
    Def qname e -> do
      (args, lets, ald) <- elimsToCExpr e bindnames lets ald
      (lets, ald) <- gatherDatatypeInformations qname bindnames lets ald
      return $ (
        CSpine {
          head = P.prettyShow (qnameName qname),
          args
        }, lets, ald)
    Con hd _ e -> do
      infos <- getConstInfo (conName hd)
      let dataname = case theDef infos of
                    ConstructorDefn cd -> _conData cd
                    _ -> __IMPOSSIBLE__
      (args, lets, ald) <- elimsToCExpr e bindnames lets ald
      (lets, ald) <- gatherDatatypeInformations dataname bindnames lets ald
      return $ (
        CSpine {
          head = P.prettyShow . qnameName $ conName hd,
          args
        }, lets, ald)
\end{minted}
